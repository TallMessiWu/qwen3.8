# 设计原则

这些原则的共同出发点：**读者是在用这张图学模型**，不是在看装饰。
每条规则背后都对应一个真实的误读——先讲误读，再讲规则，你才知道什么时候可以变通。

## 编号只属于真正的操作

**误读现场**：RMSNorm 页面上编了 ①重标定 ②数值对照，
读者第一眼得出的结论是"RMSNorm 层有两个操作"。
但 ② 只是 ① 的前后数值对比，根本不是一次计算。

带圈数字在读者眼里就是"这一层做的第几件事"。一旦把展示性内容也编号，
层的复杂度就被凭空放大了。

**规则**：编号圆圈只发给会改变数据的计算步骤。其余三类各有专门的表达：

| 内容 | 表达方式 | 视觉 |
|---|---|---|
| 真正的操作 | `opStep(n, …)` | 实心编号圆圈 + 连接线 |
| 输入数据本身 | `opSource(…)` | 虚线框 + `IN` 标记，不编号 |
| 结果展示 / 数值对照 | `opSub(…)` | 步骤内部的灰色次级区，不编号 |
| 并行分支 | `opParallel(…)` | 同一编号内并列，带"并行"标签 |

**并行尤其要小心**：图像分支和文本分支同时进行，如果编成 ①图像 ②文本，
读者会以为必须先处理完图像才轮到文本。正确做法是把它们并列在同一个编号里，
并显式写上"两条分支互不依赖"。

**顺带建议**：当某层确实只有一个操作时，在说明里直接点破
（"这一层只有一个操作"），并说清它**不做**什么
（RMSNorm 没有均值中心化、没有偏置；Embedding 没有矩阵乘法）。
读者对"少"的疑虑往往比对"多"更大。

## 同一份数据在移动

整张图的叙事是：一份数据从请求进来，被每个模块依次改造，最后变成文字。
这个"连续性"要靠动画本身传达——一个载荷在模块间移动，每站就地改变
类型、shape、数值和配色。

**不要**把这件事写进标签。曾经用过 `SAME DATA` 标签，结果被读成
"Simulated Data" 的缩写。动画已经说明了连续性，标签重复说反而制造歧义。
载荷上只留一个标注**数值可信度**的标签（"模拟数据"）。

**载荷不能遮挡卡片**。早期把载荷做成方块盖在卡片上，
结果当前模块的标题和说明全被挡住——恰恰是读者最想看的那个模块。
正确做法是让载荷停在卡片**下方**的专属通道里，用尖角指回卡片：

- 载荷做成横向条（左侧名称+shape，右侧数据网格），高度压到 60px 左右
- 行间距要为它留出通道（约 100px）
- 停靠锚点放在卡片下方（`bottom:-64px` 这类），载荷以锚点为中心
- 边列要钳制 x 并让尖角单独跟随（见 layout-pitfalls）

判断标准很简单：**停稳时载荷与任何卡片的矩形都不相交**。

## 总图：换行、有内容、当前态明确

**换行而非横向滚动**。模块一多，固定列宽必然溢出。用
`repeat(auto-fill,minmax(220px,1fr))` 让它自动换行，宽屏多列、窄屏少列。
行末的卡片把 `→` 换成 `↵`，读者才知道要接着看下一行
（靠比较相邻卡片的 `offsetTop` 判断，resize 后要重算）。

**每张卡片必须有实质内容**。只有标题的卡片等于让读者非点开不可。
每张卡至少给三样：一句话说明、这一站做什么操作、数据形态怎么变。

```
① MODULE 03 / 8
Embedding
整数索引查表，得到连续向量
─────────────
操作   E[input_ids]
形态   [1,T] → [1,T,8192]
```

**当前模块整卡高亮**，而不是加一个小圆点。早期在每张卡中间画了停靠圆圈，
既占地方又没信息量，读者还会以为那是个接口。高亮用边框加粗 + 光晕 + 微上浮
就够了，定位锚点做成零尺寸不可见元素即可。

## 状态控制台常驻可见

读者的核心问题是"数据进这一站之前是什么、出来变成什么"。
如果这个信息放在页面底部，他们就得在卡片和说明之间反复滚动。

把"进入 / 操作 / 离开"三段做成 sticky 控制台钉在总图顶部，随载荷实时更新：

```
MODULE 5 / 8   Final Norm 已完成计算：数据变为 normalized hidden   [1,T,8192]
进入 decoder hidden x₉₂·[1,T,8192] │ RMSNorm │ 离开 normalized hidden·[1,T,8192]
```

sticky 很容易被祖先的 overflow 破坏，务必用 `auditSticky()` 验证它真的钉住了。

## 重复结构只画一组

92 层 Decoder 不要画 92 个方块。画一组配方（例如 `3×GDN + 1×GQA`），
再用徽章标注 `×23 = 92 层`。这样读者一眼看到的是**结构规律**而不是一堵墙。

**FFN / MoE 要画在每层内部**，不能作为独立的一站排在 Decoder 后面——
那会让人以为整个骨干跑完才过一次 FFN。用上下两半表达：
上半是序列混合器（Attention / GDN），下半是该层自己的 FFN 或 MoE。

配方里的色块要足够大（高度 ≥ 38px、字号 ≥ 10px）。它们既是信息也是下钻入口，
太小既读不清也难点中。

## 事实与示例必须分级

这类页面最大的风险是**读者把示意数字当成真实配置**。

- **架构事实**（层数、hidden、头数、词表、中间维）必须来自官方 `config.json`。
  没有公开 config 就如实标注 TBD，**绝不能**拿近似模型的数字顶替——
  "同系列同参数量"不构成依据。
- **页面里所有小数**（张量值、注意力分数、logits、专家 ID、概率）都是编出来的，
  必须常驻标注"模拟数据"。张量面板的标注做成常驻角标，不要只在页脚写一句。
- 每个张量面板同时给出**完整逻辑 shape** 和**当前切片坐标**
  （`[B,128,128,128]` / `[0,head 0,0:4,0:4]`），读者才知道自己在看哪一块。
- 用徽章把可信度分档：配置事实 / 参考实现 / 引擎相关 / 模拟数据 / 尚未公开。

改模型时先核对 config，再改图。顺序反了很容易留下上一个模型的残留数字。
