这个 PR 在做什么

先把范围和边界钉死，免得评审时在「它该不该管 X」上绕圈。

0.1一句话与边界

让昇腾 A5 上的 Qwen3.8（hybrid 结构、head_dim=256、GQA 24Q/4KV） 把 KV cache 存成 FP8 E4M3 + E8M0 scale，attention 换成 cann_ops_transformer 里的 QFA 双算子，并且全程支持 FULL 图捕获与 MTP 投机解码。

实现方式是 vllm-ascend 一贯的插件路子：不改 vLLM。整条 C8 路径收在一个新后端 vllm_ascend/attention/c8_mxfp_v1.py 里，由量化方法在 create_weights 时 直接改写 layer.attn_backend 和 layer.impl.__class__ 装上去， 不走 backend registry——所以非 C8 的部署根本不会 import 到它。

值得在会上点一句

这个后端把所有不支持的场景都显式 raise 了，没有一处静默降级。 PCP/DCP、非因果 attention、滑动窗口、hamming sparse、非 Mooncake 的 PD connector、 缺少四元组的 kv_cache——全部抛异常并说清为什么。 对一个要进上游的硬件后端来说，这是比功能本身更该被肯定的部分。

板块 1显存

两元组变四元组

整个 PR 最有传播性的一个决定：KV cache 从 (k, v) 变成 (k, v, k_scale, v_scale)。 框架里每个假设「KV cache 就是两个张量」的地方都要跟着动。 

kv_cache = (k_fp8, v_fp8, k_scale, v_scale)
#            ↑ e4m3   ↑ e4m3   ↑ e8m0    ↑ e8m0
#            每 32 个数值配 1 个 scale 字节

基类里的两个搬块函数被改成对任意长度元组通用，注释直说是为了让 scale cache 跟着 K/V 一起换： 

# attention_v1.py:117-137
for src_cache, dst_cache in zip(src_kv_cache, dst_kv_cache):
    dst_cache[dst_indices] = src_cache[src_indices].to(dst_cache.device)

vllm_ascend/attention/attention_v1.py:114-137

1.1把 scale 字节打进 head_size

难点是显存预算。上游的 KVCacheManager 按 page_size_bytes 算能开多少块， hybrid 还要求所有 spec 的页大小统一。如果老老实实告诉它「这层有四个张量」， 要动的上游代码就没边了。

这里的做法是把 scale 字节伪装成 head_size 的一部分： 

# model_runner_v1.py:6152-6168
head_size = spec.head_size + spec.head_size // MXFP8_GROUP_SIZE   # 256 + 8 = 264
kv_cache_spec[layer_name] = FullAttentionSpec(
    block_size=spec.block_size,
    num_kv_heads=spec.num_kv_heads,
    head_size=head_size,
    dtype=torch.float8_e4m3fn,
)

上游看到的就是一个普通的 fp8 full-attention 层，页大小、块数、页对齐全都自动对。 代价是从此 spec.head_size 不再是真实 head dim， 下游每个消费点都得记得还原： 

# model_runner_v1.py:5224-5232 —— 还原真实维度
ori_k_dim = k_dim // (1 + MXFP8_GROUP_SIZE) * MXFP8_GROUP_SIZE   # 264 // 33 * 32 = 256
这是本 PR 的主要认知负担

「打包的 head_size」这个约定在 model_runner_v1.py 里有 7 个分支要照顾 （5224 / 5283 / 5596 / 5642 / 5699 / 5751 / 5815）。 它换来的是上游一行不用改，但也意味着以后任何人碰这段都要先知道这个约定。 评审时可以问：这些分支能不能再往 mxfp_kv_cache.py 里收一层。

1.2一块预算切四份

拿到打包后的总预算，按四个 payload 的字节比例切开，每层私有四个 int8 buffer： 

# model_runner_v1.py:5233-5248
kv_head_dim_list = [ori_k_dim, ori_v_dim,
                    ori_k_dim // MXFP8_GROUP_SIZE, ori_v_dim // MXFP8_GROUP_SIZE]
#                  [256,       256,       8,   8]  →  切分因子
(k_tensor_split_factor, v_tensor_split_factor,
 k_scale_tensor_split_factor, v_scale_tensor_split_factor) = calc_split_factor(kv_head_dim_list)

注释特意强调「每个共享层都拥有自己的 4 元组，所以 block index 不会跨层串」—— 这正是 C8 这类多缓冲布局最容易出的事故，写进注释是对的。

1.3PA_NZ 的两个 scale cache

K/V 本体保持自然的 4 维 (num_blocks, block_size, num_kv_heads, head_dim)—— 分配、hybrid 切分、PD 传输、prefix-cache CoW 全都看这个形状，所以它们统统不用改。 只在调算子的那一刻取一个 5 维 NZ 视图。两个 scale cache 则直接按算子要的 6 维形状分配， 谁也不用在 attention 时转置：

张量形状D=256, Bs=512, N=4 时
K / V cache（存储）[Bn, Bs, N, D][Bn, 512, 4, 256]
K / V cache（算子视图）[Bn, N, D/32, Bs, 32][Bn, 4, 8, 512, 32]
K scale cache[Bn, N, Bs/16, D/64, 16, 2][Bn, 4, 32, 4, 16, 2]
V scale cache[Bn, N, D/16, Bs/64, 16, 2][Bn, 4, 16, 8, 16, 2]

vllm_ascend/attention/mxfp_kv_cache.py:6-98（形状公式与 golden 参考出处都写在文件头注释里）

显存账是 33/32：每 32 字节数据多带 1 字节 scale，相对 bf16 仍然省掉将近一半。 注意 K 和 V 的 scale 页大小完全相等，UT 里专门断言了这点。

一个可以问的设计取舍

V 的 scale 是静态 per-channel的——每个 head 其实只有 head_dim 个字节有信息量， 却按整页存了一份，占用和逐 token 变化的 K scale 一样多。 换来的是算子能直接按 PA_NZ 读，不需要在 attention 里做广播。 这是个明确的「用显存换 kernel 简单」，评审时值得让作者确认一下这是刻意的。

2.1三代命名与 FAKQuant 让位

ModelSlim 导出 V scale 的键名换过三次，三代都要认：

checkpoint 里的名字映射到坑
.v_proj.kv_cache_scale.attn.v_cache_scale直接映射
.attn.v_scale.attn.v_cache_scalevLLM 自己的正则已先把 v_proj.v_scale 改成了这个名字，必须按改名后的抓
.fa_v.scale.attn.v_cache_scale复用了 FAKQuant 的键名做另一种 recipe
 
# modelslim_config.py:466-477
# ... 否则它落到一个本方案从没注册过的参数上，被静默丢弃
# （vendored-QFA bring-up 期间就因为这个，整整一次服务都在用 127 兜底值跑）
suffix_map[".attn.v_scale"] = ".attn.v_cache_scale"

更要紧的是 FAKQuant 让位。同一层可能同时声明了顶层 fa_quant_type 和逐层的 MXFP8 quant_type；两者是同一个 KV cache 的两套 recipe， 而 get_quant_method 先测 FAKQuant，它必赢。赢了之后它的权重映射会把 fa_v.scale 改名进一个 MLA 子模块——dense 模型根本没有那个模块，scale 就没了。 所以检测到 MXFP8 就直接把 FAKQuant 关掉： 

# modelslim_config.py:1003-1015
if self.enable_fa_quant:
    logger.warning_once("fa_quant_type=%s is declared alongside an MXFP8 KV cache; ignoring FAKQuant.", ...)
    self.enable_fa_quant = False

顺带把 K/Q 的 FAKQuant 参数（fa_q.scale / fa_k.scale / 两个 offset） 声明为「可忽略」——MXFP8 下 K、Q 是运行时动态量化的，这些 checkpoint 里的 scale 没有参数可落， 不声明的话 AutoWeightsLoader 会直接拒收整个 checkpoint。

2.2TP 切分按 KV head 数，不是按 tp_size

scale 是「每个 (kv_head, channel) 一个 E8M0 字节」，所以切分的单位是 KV head。 按 tp_size 去除会在两个方向上出错。加载器处理三种情况：

情况 A

checkpoint 只存一套通道 scale

所有 KV head 共用。repeat 平铺到本 rank 的 head 数，后面的 narrow 成为 no-op。

情况 B

每个 head 一套

num_kv_heads ≥ tp_size，退化成普通的连续 narrow。TP2：rank0 拿 [0,256)，rank1 拿 [256,512)。

情况 C

head 数少于 rank 数

GQA 下 vLLM 会复制 KV head：TP4 两个 head，rank 0/1 都拿 head 0，rank 2/3 都拿 head 1。 src_head = tp_rank // (tp_size // num_heads_total)。

vllm_ascend/quantization/methods/kv_cache/mxfp_c8.py:8-50 · UT 把三种情况都钉死了

另外 ModelSlim 把 scale 导成列向量 [hidden, 1]，而参数是一维的，所以先 flatten()。

2.3127 兜底、0 通道、offset 必须为零

E8M0 是纯指数、偏置 127，所以字节 127 表示 2⁰ = 1.0，是中性值。它被用在两处： 

# ① checkpoint 缺这一层的 v_cache_scale 时，参数初值就是 127（而不是未初始化内存）
torch.full((hidden_size,), 127, dtype=torch.uint8)

# ② 校准器给某个通道吐了 0 时，就地换成 127
if bool((raw == 0).any()):
    raw[raw == 0] = 127

vllm_ascend/quantization/methods/kv_cache/mxfp_c8.py:88-127

为什么 0 必须被换掉：E8M0 的 0 表示 2⁻¹²⁷。它有两个消费者， 两边都会炸——量化时的倒数会变成 2¹²⁷（任何非零激活直接 inf）， 写进 V scale cache 的原始字节则会让该通道反量化后归零。注释明说这是真实 checkpoint 上踩到的。

最后是 offset。有些 recipe 会跟着 FAKQuant 的模板顺手导出一个 V offset， 但 MXFP8 per-channel 和 QFA 算子都是对称量化，唯一正确的值是 0。 这里的处理很值得学：不是无视它，而是注册参数把它读进来、然后断言为零。 

# mxfp_c8.py:109-117 —— "loading it is how that gets checked rather than assumed"
if bool(offset.any()):
    raise RuntimeError("V cache offset is non-zero ... cannot be served by this scheme")
板块 3写 cache

写 cache

这一章是热路径：每层每步都跑。所以每一个 kernel 都要问「能不能不跑」。

3.1PA_NZ scatter 与那个不能省的 cache_mode

K/V 本体用的是 FIA C8 路径已经在用的 npu_scatter_pa_kv_cache， 关键是必须声明 cache_mode="PA_NZ"。注释里这句话写得很好，值得念给会上听：

mxfp_kv_cache.py:220-227

不传这个参数，算子会按场景 2（"Norm"，[num_blocks, block_size, num_head, head_size]） 去读 cache，那个布局的 dim2 是 num_head—— 「shape contract requires key_cache.dim2 == num_kv_heads」这条报错就是这么来的。 轴序不是问题，漏了 mode 才是。

另外所有张量都走 int8 视图再交给算子。算子确实接受 FLOAT8_E4M3FN， 但只在 950PR/950DT 上；A2/A3 只认 FP16/BF16/INT8，而 INT8 到处都认。 两者 sizeof 都是 1，写进去的字节完全一样——少一个随产品变化的假设。 （这条和我们仓里那条「NPU 上 FP8 张量必须用字节视图搬运」是同一条规矩的第 N 次出现。）

负数 slot（vLLM 的 PAD_SLOT_ID）不 clamp 也不过滤，原样交给算子跳过。 这样 padded batch 不花额外代价，形状对图捕获也保持静态。

3.2K scale：三个 kernel 压成一个

K 的 scale 是逐 token 的，每层每步都要 scatter 一次。原来的写法是 读 + select + 写——先把 cache 里的旧内容 gather 出来， 对 padding 行用 where 选回旧值，再整体写回。三个 kernel， 只为了让「只有 FULL 图 replay、MTP verify 和 draft 步才会出现」的 padding 行变成 no-op。

现在是一个： 

# mxfp_kv_cache.py:313-316 —— padding 行 clamp 到 slot 0
safe_slots = slot_mapping.to(torch.long).clamp(min=0)

# mxfp_kv_cache.py:353 —— 一次 index_put_，没有读，没有 where
key_scale_cache[block_ids, :, seg_ids, :, frag_ids, :] = key_scale

能这么做是因为 slot 0 属于 block 0，而 vLLM 的 BlockPool 把 block 0 当 null block 从空闲表里摘掉了，永远不会发给任何请求。padding 行写脏它没有任何真实 token 会读到； 唯一会读的是给捕获批次凑数的 dummy 请求，而它们的输出本来就丢弃。

UT 把这个取舍写成了两条断言

test_prefill_shaped_batch_is_bit_identical_to_the_read_modify_write： eager 批次按真实 token 数切过，没有 −1 行，新旧实现逐位相同。
test_padded_decode_batch_differs_only_in_the_null_slot： FULL replay 的 padding 批次，新旧实现只在 null slot 上不同。
这比「测了新实现能跑」有说服力得多——它把「哪里允许不一样」也写进了合同。

还有一条 UT 用 TorchDispatchMode 数 aten op，直接断言 「有且只有一次 index_put_，零次 index/where」。 在 NPU 上一个 aten op 就是 profile 里的一行、捕获图里的一个节点，这个断言是有物理意义的。

3.3V scale：建 cache 时填一次

V 的 scale 是静态的，推理期间永不改变，所以它根本不该出现在 attention 路径上。 现在在 initialize_kv_cache_tensors 里填一次： 

# model_runner_v1.py:4763-4764
# Static V scales are written once, here, and never again.
self._fill_c8_mxfp_v_scale_caches(kv_caches)

这就是「图模式 MTP 接受率塌」那个故障的正式修法。当时的写法是在 forward 里惰性填、 并用一个 Python 标记记住「填过了」。ACL 图捕获只记录不执行， 而那行记录「填过了」的 Python 是真执行的——于是 draft 模型第一次走到这段就是捕获本身， V 的 scale cache 永远全零、反量化后 attention 恰好吐零，一开 draft 图接受率就塌。

注释把这段历史完整留下了，并且指出「即使加了守卫，另一条路是每次 replay 重新广播整个 cache」—— 两条路都不好，而「在任何请求、任何捕获、任何 replay 之前填一次」两个问题都没有。

配套的防御：C8 层如果拿到的不是四元组，直接 raise。 注释写了理由——「一个 V scale 没落地的 C8 层看起来像模型质量问题，不像配置问题， 这个误诊已经浪费过一轮排查」。

板块 4attention

QFA 双算子

QFA 是两个算子：一个在 AICPU 上算「这批数据怎么分给各个核」（metadata / plan）， 一个在 AICore 上照着这个计划干活。这一章全是围绕「怎么少调前者、怎么让后者挑对 kernel」。

4.1每步一个 plan，23 层共享

plan 的输入是：头数、head dim、quant mode、两个长度张量、mask mode、window、四个 layout。 没有一个是分层的。而 Qwen3.8-2.4T 一步要走 23 个 full-attention 层。 所以 plan 按「全部非张量输入」做 key 缓存在这一步的 AscendMetadata 上，一步只算一次： 

# c8_mxfp_v1.py:419-427
plan_key = (self.num_heads, self.num_kv_heads, self.head_size,
            max_seqlen_q, mask_mode, layout_q_descale)

省掉的是每层一次 AICore→AICPU 往返，而且这个往返的开销随 batch 增长。

这里推翻了一个之前的判断

旧代码在捕获期会绕过缓存，让每层各发一次 metadata 算子， 理由是「捕获里的调用必须消费自己刚产生的 plan」。 本 PR 的结论是算子契约没有这个要求——主算子把 metadata 声明为只读 Input， 从不写回，所以多层共享一个 plan 互不干扰。 UT test_capture_shares_the_plan_too 专门作为回归护栏钉死「没有 bypass 路径了」。

4.2max_seqlen_q 是最长单条，不是批总量

这是个很典型的「传错了也不报错、只是慢」的坑。metadata 算子用这个属性初始化 querySeqSize，然后对每条请求做 max(attr, 本条长度)—— 只会往上调，永远不会调回来。

所以传小了算子会自己纠正，传大了就一直大。旧代码传的是批 token 总量： 一个 256 请求的 decode 步，每条 query 长度都是 1，却声明了 256—— 整步都按「最长 256」去排布。改成 max_query_len， 而这个量 _prepare_inputs 已经在 CPU 上算好了，既不用 device 同步也不用 host 规约。

4.3q scale 的 layout 就是选 kernel

MXFP8 的 q scale 可以按两种布局传，而这个选择就是在选 kernel 模板：

layout形状编译出的模板什么时候用
TND(Q_T, Q_N, D/64, 2)prefill量化算子的原生输出，不动
N2TGD(KV_N, Q_T, G, D/64, 2)decodeG × Q_S ≤ 80

两种布局装的是同一批 scale，所以选错只是慢，不会算错。 N2TGD 把 query head 轴拆成 (KV_N, G) 再把 KV head 那半提到 token 轴前面， 让一个 kv head 的整组连续——因为 query head 本来就是 GQA 连续排列的（head n 服务 kv head n // G）， 所以拆分是纯 reshape，剩下的是 permute。

两个细节值得看：

  • permute 走字节视图。transpose 和 .contiguous() 背后的 copy 对 float8 要么直接报错、要么回退 AICPU 把 device 卡死，所以先 view(torch.uint8)， 到调算子时再 bitcast 回 E8M0。
  • 判据读 query 形状，不读 attn_state。 UT 写了回归护栏：如果按 attn_state == DecodeOnly 判断， 一旦开 MTP 就永远不会命中——MTP verify 步是 SpecDecoding， 每条 1 + num_spec 个 query token，它该走 decode 模板。

兜底也做了：num_kv_heads == 0 或者 head 数不能整除（MTP draft 层可能出现）， 直接退回 TND，而不是产生一个错位的布局或者 ZeroDivisionError。

4.4NO_MASK 是一维 tiling key

当这一步每条请求都只有一个 query row 时，mask 直接不传： 

# c8_mxfp_v1.py:665
mask_mode = QFA_MASK_MODE_NO_MASK if max_seqlen_q == 1 else QFA_MASK_MODE_CAUSAL

hasAttenMask 是算子六维 tiling key 中的一维，所以 NO_MASK 不是省一次 load，而是换了一个从不读 mask 的 kernel 模板。 在 Q_S == 1 时它和 CAUSAL 完全等价：唯一那行 query 本来就能看 [0, seqused_kv) 全部， KV 范围由 seqused_kv 而不是 mask 界定。

MTP verify（Q_S = 1 + num_spec）保留 CAUSAL，MTP draft（Q_S == 1）不保留——分得很清楚。

还有一个整体设计：一步只调一次 QFA，prefill 和 decode 请求混在一起， 而不是 FIA 时代的按子集分别调用。因果 mask 本来就覆盖 decode 行， 而且喂给算子的批次更小。PrefillNoCache 也走 cache—— reshape_and_cache 在 attention 之前已经把这一步的 K/V 写进去了。

5.2为什么跨层缓存这次是安全的

这是整个 PR 里最需要讲清楚的一段推理，因为它表面上看像是在重复老错误： 「把一个值缓存起来给后面的层用」，听着就像被烘死。

关键区别

捕获不能容忍的是在捕获区之外产生的值，因为 replay 从不重跑 Python。 而这些派生调用本身就在捕获区里： 第一层的派生被记录下来，其余层只是消费它产生的那个张量， 每次 replay 都会对着刷新过的 buffer 重新执行那一次派生。

同理，max_seqlen_q / layout / mask_mode 这几个 Python 标量在捕获时确实被烘死了， 但这是安全的——它们读的是 max_query_len， 正是 vLLM 用来判定「这是一张 uniform-decode 图」的同一个量， 所以捕获和它的每一次 replay 必然一致。而且 metadata 算子的 max() 只上调不下调， 即使偏小也会被算子自己纠正。

MTP draft 图走的是另一条捕获路径（torch.npu.graph 的 ACLGraphWrapper）， 但 metadata 经过同一个 build()，per-step 长度也在 proposer 的常驻 buffer 里逐步原地刷新—— 同一套「地址稳定」合同。

板块 6hybrid

定容与 CoW

这一章就是 junlin-c8-mxfp-16614 那两个提交，2026-09-21 本机验证过，真机待验。

6.1按 FP8 字节重算 block

症状：换上 C8 之后，KV 容量不升反降，只有 BF16 的四分之一。 一个应该让容量翻倍的特性，实际把容量砍到 1/4。

根因是两件事撞在一起：

  1. hybrid 的配置钩子（patch_mamba_config）跑在 quant_config 赋值之前， 它看不到 C8，于是按 BF16 K/V 把 page 定成「2048 token 那么大」；
  2. 随后 refresh_block_size 又把 block 写死成 512（QFA 的 kernel 块大小）。

结果：一个能装 2048 个 BF16 token 的页，只装了 512 个 FP8 token——87% 是填充。

修法是在 refresh_block_size 里按 C8 字节把钩子的活重做一遍。 不变量还是那条：hybrid 两组共享一个页大小，所以一个 attention block 的 K payload 必须正好等于一个 SSM state，两组的 block id 才能落在不相交的字节上。 

# utils.py:1350-1364
block_size, remainder = divmod(ssm_page_size, num_kv_heads * head_size * kv_dtype_size)
if remainder or block_size % A5_C8_MXFP_KV_CACHE_BLOCK_SIZE:
    raise ValueError("C8_MXFP cannot align the hybrid KV cache: ...")
BF16 路径C8 旧逻辑本 PR
block（token）20485124096 = 8 × 512
相对 BF16 容量1×0.25×2×
页内填充—87%< 2%（只剩 conv state）

数字对应 Qwen3.8-2.4T @ TP8：SSM state (16,128,128) fp32 = 1 MiB，每 rank 1 个 256 维 KV head

不能整除就直接报错，这是对的：27B @ TP16 有 3 个 value head， 算出来 768 个 FP8 token，是 1.5 个 kernel 块。凑整会让 K 段和 SSM 段错位， 两组的 block id 串扰——那是最难查的一类 bug，宁可起不来。

6.2scheduler 块 ≠ kernel 块

block 变成 4096 之后，一个 scheduler 块对应 8 个 kernel 块。 而 prefix-cache 的 CoW 拷贝拿到的是 scheduler 块 id， hybrid 的 attention 视图却是按 kernel 块切开的。 直接拿 scheduler id 当行号，不只是拷错行，还会写进别的请求正在用的块。 

# model_runner_v1.py:948-950 —— 按每层视图自己的比例展开成 kernel 行
scale = max(cache_tensor.shape[0] // num_blocks, 1)
rows = ids.unsqueeze(-1) * scale + torch.arange(scale, device=self.device)

顺带绕开了上游 helper 的两个前提：它把整块 untyped_storage() 当 (num_blocks, page_bytes) 看，而昇腾这边 (a) PD 部署会按 2 MiB 对齐多分配，整除断言直接炸； (b) hybrid buffer 是分段的（[pad|conv|…|k|ssm|…|v|pad]）而不是块主序， 就算断言过了也会跨段拷贝。走每层视图对两种布局都对。

递归状态的视图（conv/ssm）每个 scheduler 块只占一行，scale 算出来是 1，自动退化成原来的行为。 FP8 视图则先转 uint8 再索引——aclnnIndex 不收 FP8（EZ1001），和 K scale 那里是同一个 workaround。

08争议点

评审会上的六件事

前两件是实质问题，建议合并前处理；后四件是可以当场讨论的。

①PR 描述里那个 “critical issue” 是错的

PR 正文里有这么一段（是从 Gemini 的建议摘要里整段粘进去的）：

PR 描述原文

“However, a critical issue was identified in model_runner_v1.py where k_shape is constructed incorrectly by omitting the first dimension (num_blocks), which will lead to a ValueError during unpacking … and an IndexError later.”

这个判断不成立。论证如下： 

# attention_v1.py:102-111 —— get_kv_cache_shape 返回的是 5 维
return (2, num_blocks, block_size, num_kv_heads, head_size)

# model_runner_v1.py:5768 —— 通用路径怎么用它
k_shape = kv_cache_shape[1:]                  # → 4 个元素

# model_runner_v1.py:5754 —— C8 路径
k_shape = (*kv_cache_shape[1:-1], head_dim)   # (nb, bs, n) + head_dim → 同样 4 个元素 ✓

前导的 2 本来就要去掉，[1:-1] 去掉的是尾部那个被打包过的 head_size（264），再换回真实的 256。解包成 4 个值完全正确。 本机跑的 TestC8MXFPVScaleCacheFill / TestCopyKVCacheBlocksByLayerViews 也全绿。

建议

先把 PR 描述里这段删掉。评审人第一眼会看描述， 看到作者自己承认有 critical bug，多半会直接照着追，白白烧掉一轮。

不过顺着这行往下看，倒是有两个真的隐患，值得当场提：

  • 隐含假设了 NHD 布局。 get_kv_cache_shape 在 VLLM_KV_CACHE_LAYOUT ∈ {LBHNC, HND} 时返回的是 (2, nb, n, bs, hd)。那时 [1:-1] 得到 (nb, n, bs)， 而 split_hybrid_c8_mxfp_cache_buffer 按 (nb, bs, n, dim) 解包—— 轴序会错位。C8 路径目前没有任何守卫，建议加一条断言或者直接拒绝这两种 layout。
  • v_shape = k_shape 和同一个 PR 的其它部分自相矛盾。 这里用 hf_text_config.head_dim 并且令 V 与 K 同形，等于硬假设 head_size_v == head_size； 而同一个 PR 里的 fill_mxfp_v_scale_cache（mxfp_kv_cache.py:285）和 _nz_5d_view （c8_mxfp_v1.py:281）都特意从 cache 自己读维度，注释明说是为了支持两者不等。 两种态度挑一个：要么全都支持，要么在入口处显式拒绝。

建议

结论与评审顺序建议

结构上是对的。C8 路径收进独立模块、按 sfa_v1/mla_v1 的惯例分层、 不支持的场景全部显式拒绝、每个反直觉的决定都在注释里留了理由和事故出处—— 这些是一个硬件后端进上游该有的样子。

两个实质问题都不难改：删掉 PR 描述里那段误判，还原 model_runner_v1.py:5743 那一行。

建议的评审顺序：

  1. 先定性：打包 head_size 这个总体设计能不能接受。 它决定了 model runner 里那 7 个分支存不存在，其它都是它的推论。
  2. 再看热路径：B4 和 B5。 这两章是真机上出过事故的地方，也是这个 PR 技术含量最高的部分。
